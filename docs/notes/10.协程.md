# 第 10 步：NtyCo 协程入口

> 最后一步。把网络层从 epoll 事件驱动换成协程模型。
> 你写的是同步阻塞代码，跑的是异步非阻塞性能。

---

## 协程解决了什么问题？

### 三种并发模型

**多线程模型（tinywebserver 用过）：**
```
一个连接 → 一个线程 → recv() 阻塞等数据
```
- 线程切换开销大（内核态切，寄存器全保存）
- 100 万连接就要 100 万线程，栈内存爆了
- 线程数有上限

**epoll 事件驱动（第 4 步写的）：**
```
一个线程 → epoll_wait() → 哪个 fd 就绪就处理哪个回调
```
- 不用开很多线程
- 但代码写成回调地狱：accept_cb → recv_cb → send_cb，状态机在回调之间跳
- 自己维护"这个连接现在在等读还是等写"

**协程：**
```
一个连接 → 一个协程 → recv() 等数据时自动切走
```
- 写的是阻塞代码，跑的是异步性能
- 不用写回调，不用维护状态机

### 三种模型对比

| | 多线程 | epoll 事件驱动 | 协程 |
|---|---|---|---|
| 写法 | 顺序阻塞 | 回调+状态机 | 顺序阻塞 |
| 切换开销 | 大（内核态） | 无回调 | 小（用户态） |
| 并发量 | 几千线程 | 几万~几十万 | 几十万~百万 |
| 代码复杂度 | 简单 | 痛苦（回调地狱） | 简单 |
| 谁切换 | 内核 | 你自己写回调 | 协程库 |

### 为什么协程切换比线程快？

| | 线程切换 | 协程切换 |
|---|---|---|
| 在哪切 | 内核态 | 用户态 |
| 要切什么 | 全部寄存器、TLB、调度器 | 只切栈指针和 PC |
| 耗时 | ~1-2μs | ~几十 ns |
| 谁触发 | 操作系统 | 协程库自己 |

> 协程 = 用同步阻塞的写法，拿到异步非阻塞的性能。

## 完整代码 `ntyco_entry.cpp`

```cpp
#define _GNU_SOURCE
#include "kvstore.hpp"

// NtyCo 头文件会重定义 RB_RED/RB_BLACK，先撤销我们的
#undef RB_RED
#undef RB_BLACK

// 只在 include NtyCo 期间屏蔽 void* 转换警告
#pragma GCC diagnostic push
#pragma GCC diagnostic ignored "-Wpermissive"
extern "C" {
#include "nty_coroutine.h"
}
#pragma GCC diagnostic pop

#include <arpa/inet.h>
#include <cstdio>
#include <cstring>

// 每个连接的协程：同步阻塞写法，底层自动切换
void server_reader(void *arg) {
    int fd = *(int *)arg;

    while (1) {
        ConnItem item;
        memset(&item, 0, sizeof(item));

        // recv 看起来是阻塞的，但协程库在等数据时切走
        int ret = recv(fd, item.rbuffer, BUFFER_LENGTH, 0);
        if (ret > 0) {
            kvstore_request(&item);
            item.wlen = strlen(item.wbuffer);
            send(fd, item.wbuffer, item.wlen, 0);
        } else {
            close(fd);
            break;
        }
    }
}

// server 协程：accept 循环
void server(void *arg) {
    unsigned short port = *(unsigned short *)arg;
    free(arg);

    int fd = nty_socket(AF_INET, SOCK_STREAM, 0);
    if (fd < 0) return;

    struct sockaddr_in local;
    local.sin_family = AF_INET;
    local.sin_port = htons(port);
    local.sin_addr.s_addr = INADDR_ANY;
    bind(fd, (struct sockaddr *)&local, sizeof(local));
    listen(fd, 20);
    printf("listen port: %d\n", port);

    while (1) {
        struct sockaddr_in remote;
        socklen_t len = sizeof(remote);
        int cli_fd = accept(fd, (struct sockaddr *)&remote, &len);

        // 每来一个连接，创建一个新协程
        nty_coroutine *read_co;
        int *pfd = new int(cli_fd);
        nty_coroutine_create(&read_co, server_reader, pfd);
    }
}

// 入口：替代 epoll_entry
int ntyco_entry(void) {
    nty_coroutine *co = nullptr;
    unsigned short *port = new unsigned short(9096);
    nty_coroutine_create(&co, server, port);  // 创建 server 协程
    nty_schedule_run();                        // 启动调度器，永不返回
    return 0;
}
```

`kvstore.cpp` 的 main：
```cpp
int main() {
    init_kvengine();
    ntyco_entry();
    exit_kvengine();
    return 0;
}
```

## 核心知识点

### 三个关键 API

| API | 作用 |
|---|---|
| `nty_coroutine_create(&co, func, arg)` | 创建协程，指定函数和参数 |
| `nty_schedule_run()` | 启动调度器，跑所有协程，不返回 |
| `nty_socket/bind/listen/accept/recv/send` | 协程版系统调用，阻塞时自动让出 CPU |

### 为什么 `recv` 不占 CPU？

协程库底层用 epoll。当你调 `recv` 时：
1. 协程库检查 socket 有没有数据
2. 没有 → 把当前协程挂到 epoll 等待队列，切到别的协程跑
3. 数据来了 → epoll 通知，切回这个协程继续

### 协程版 vs epoll版写法对比

**epoll 版（割裂的回调）：**
```cpp
void recv_cb(...) {
    recv(fd, buf);
    kvstore_request();
    set_event(fd, EPOLLOUT);   // 切到 send 状态
}
void send_cb(...) {
    send(fd, buf);
    set_event(fd, EPOLLIN);    // 切回 recv 状态
}
```

**协程版（顺序代码）：**
```cpp
while (1) {
    recv(fd, buf);          // 等数据，没数据就切走
    kvstore_request();      // 处理
    send(fd, buf);          // 发响应，发完就切走
}
```

## 深入讨论：extern "C"

### 为什么需要？

C 和 C++ 编译函数名的方式不同：

- **C：** 函数编译后名字就是原名 `nty_coroutine_create`
- **C++：** 因为支持函数重载，编译器会"加密"函数名（name mangling），变成类似 `_Z20nty_coroutine_createP14nty_coroutinePiPv`

NtyCo 是 C 库，编译出来的函数名是原名。你的 `.cpp` 是 g++ 编译的，去找时按 C++ 规则找加密名，两边对不上 → 链接错误。

```cpp
extern "C" {
#include "nty_coroutine.h"
}
```

告诉 C++ 编译器：大括号里的函数按 C 的方式链接，不要加密名字。这样 g++ 找 `nty_coroutine_create` 时就找原名，和 C 库对上了。

**自己写的 .cpp 不需要这个，都是 g++ 编译，两边都加密。只有调用 C 写的第三方库时才需要。**

## 深入讨论：编译问题排查

### 问题 1：`ntyco_entry` was not declared

`kvstore.hpp` 里没声明。加一行：
```cpp
int ntyco_entry(void);
```

### 问题 2：`RB_BLACK` redefined

NtyCo 头文件自己也定义了 `RB_BLACK=0`（它内部用红黑树管理协程），和你的 `RB_BLACK=2` 冲突。

解决：include NtyCo 之前先撤销：
```cpp
#undef RB_RED
#undef RB_BLACK
extern "C" {
#include "nty_coroutine.h"
}
```

`kvstore_rbtree.cpp` 不 include NtyCo，用的还是你自己的值，互不影响。

### 问题 3：`invalid conversion from void* to nty_schedule*`

NtyCo 是 C 代码，C 里 `void*` 可以随便转，C++ 不行。两种解法：

- **编译加 `-fpermissive`**（变成 warning）
- **改 NtyCo 头文件第 271 行**加强转：
  ```c
  return (nty_schedule *)pthread_getspecific(global_sched_key);
  ```

### 问题 4：`_GNU_SOURCE` redefined

在文件最开头（所有 include 之前）先定义：
```cpp
#define _GNU_SOURCE
```

### 用 pragma 精准屏蔽警告

不想加 `-w` 屏蔽所有警告的话，用 pragma 只屏蔽这一个：

```cpp
#pragma GCC diagnostic push
#pragma GCC diagnostic ignored "-Wpermissive"
extern "C" {
#include "nty_coroutine.h"
}
#pragma GCC diagnostic pop
```

- `push` 记录当前警告状态
- `ignored` 临时关闭指定警告
- `pop` 恢复原来的状态
